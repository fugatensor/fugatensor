# 矩阵乘法与提交优化

本轮将 CPU fp32 矩阵乘法接到 OpenBLAS，并允许 CUDA fp32 矩阵乘法使用 TF32。单 GEMM 继续录入 CUDA Graph，构图到提交之间直接传递存储对象，端口描述和输出分配规则在准备时固定。


<a id="comparison"></a>

## 完整调用延迟

CPU 1024 阶 GEMM 的完整调用从 **142.20 ms 降到 31.73 ms，耗时降低 77.7%**，Torch eager 为 29.23 ms。CUDA 1024 阶从 **223.81 μs 降到 175.72 μs，降低 21.5%**，同样允许 TF32 的 Torch 为 152.35 μs。小 CPU GEMM 仍主要受调用层影响。

下表使用非二进分数输入，单位 μs。修改前 CUDA 采用 IEEE，新版和 Torch 允许 TF32；CPU 均为 fp32。每项为三轮中位数，原始样本及范围见[GEMM 对照](assets/blas-tf32-optimization/steady/matmul-scaling.csv)。

| 设备 | 阶数 | 修改前 Fuga | 当前 Fuga | Torch eager | Fuga 耗时下降 |
| --- | ---: | ---: | ---: | ---: | ---: |
| CPU | 16 | 44.0 | 35.5 | 3.4 | 19.4% |
| CPU | 128 | 184.0 | 114.5 | 71.7 | 37.8% |
| CPU | 512 | 17,947.2 | 3,989.7 | 3,720.7 | 77.8% |
| CPU | 1024 | 142,198.6 | 31,727.3 | 29,232.1 | 77.7% |
| CUDA | 16 | 102.4 | 93.3 | 73.3 | 8.9% |
| CUDA | 128 | 106.1 | 96.7 | 79.4 | 8.8% |
| CUDA | 512 | 126.5 | 106.3 | 88.3 | 15.9% |
| CUDA | 1024 | 223.8 | 175.7 | 152.4 | 21.5% |

在 CUDA 1024 阶的同 IEEE 控制中，新版 Fuga 为 **203.72 μs**，Torch 为 **210.17 μs**。开启 TF32 后，Fuga 降到 **175.72 μs**；这组控制将调用路径变化与精度策略变化分开记录。[完整 IEEE/TF32 控制](assets/blas-tf32-optimization/steady/ieee-control.csv)。

逐元素融合、归约链和分支汇合也按相同流程对照。其 large 负载的 Fuga 耗时观测下降约 2.4%–11.4%；原始三轮范围见[整体负载](assets/blas-tf32-optimization/steady/main-latency.csv)。全部五组共 **288 项、9,216 个样本**通过数值、执行计数和数据一致性校验。

## 开销落在哪一层

分层探针在独立进程中预热至少 1 秒，记录 101 个样本。构图、根节点收集、缓存查找、后端调用及结果发布分别计时；后端调用包含输出分配，CUDA 同步单独记录。下表是各段中位数，完整调用采用上一节的直接计时。

| 阶段（μs） | CPU 16 修改前 | CPU 16 当前 | CUDA 128 修改前 | CUDA 128 当前（IEEE） |
| --- | ---: | ---: | ---: | ---: |
| Python 构图入口 | 7.56 | 7.64 | 11.83 | 11.38 |
| 原生收集与执行键 | 8.15 | 7.93 | 10.91 | 10.13 |
| 缓存查找 | 0.80 | 0.80 | 1.08 | 1.08 |
| 后端调用 | 19.53 | 12.04 | 61.65 | 37.22 |
| 发布结果 | 1.82 | 0.81 | 2.68 | 1.52 |

CPU 16 阶预分配原生函数调用约 **1.28 μs**；完整 Fuga 调用为 **35.45 μs**，Torch eager 为 **3.41 μs**。小矩阵的剩余差距集中在构图、收集、存储分配与调用边界。CUDA 128 阶预分配 ASK 提交由 **17.18 μs 降到 16.61 μs**；Fuga 后端段的更大降幅来自去除 Tensor 包装和 Python 端口循环。[分层原始数据](assets/blas-tf32-optimization/layers/summary.csv)。

Nsight Systems 2026.1.3 在持续预热后捕获每个尺寸的 51 次调用，按 Graph 节点记录实际 kernel：

| 阶数 | Fuga IEEE kernel（μs） | Fuga TF32 策略 kernel（μs） | Torch TF32 策略 kernel（μs） |
| --- | ---: | ---: | ---: |
| 16 | 2.18 | 3.23 | 3.23 |
| 128 | 5.31 | 5.28 | 5.38 |
| 512 | 43.04 | 45.89 | 23.39 |
| 1024 | 111.58 | 85.64 | 72.41 |

128 阶 ASK 选择普通 SGEMM；512/1024 阶选择 TF32 Tensor Core kernel。1024 阶的设备计算因此从 111.58 μs 降到 85.64 μs。当前库策略在 512 阶选择的 kernel 仍慢于 Torch；trace 显示 ASK 使用 `align1`，Torch 使用 `align4`，1024 阶的 tile 也不同。进一步优化应针对准备阶段的对齐契约和算法选择，保持公开端口语义统一。[kernel 名称及 CUDA API 记录](assets/blas-tf32-optimization/trace/summary.csv)。

**matmul 已录入 CUDA Graph。** 每个测量进程只实例化一次 Graph；稳定地址时节点更新为 0。Nsight 的每个 Fuga 区间记录了 **51 次 `cuGraphLaunch` 和 51 次 GEMM kernel**。Graph replay 复用了 cuBLASLt 子图。[Graph 计数](assets/blas-tf32-optimization/steady/graphs.csv)。

## 实现与依赖

CPU fp32 由 ASK 生成 `ask_cblas_sgemm` 调用。OpenBLAS 0.3.33 的源码摘要与构建配置由依赖锁固定，原生 SDK 收据与锁核对；本轮采用单线程、LP64 接口。矩阵尺寸、前导维度和临时区生存期在编译时校验；表达式输入先在融合区域物化。CPU fp16 保留 ASK 自有逐 K 的 fp32 乘加实现，CPU 类型集合保持 bool/i32/i64/f32/f16。

Host ABI 用 `link_libraries` 声明库名，Compiler capabilities 提供实际库路径。Fuga 按这一契约链接目标文件，wheel 携带带 ASK 前缀的 OpenBLAS 共享库与许可证。ASK 的 Compiler/Runtime SDK 仍可独立消费，Compiler 消费测试关闭了 LLVM/MLIR SDK 搜索。

CUDA fp32 的 cuBLASLt compute type 为 `CUBLAS_COMPUTE_32F_FAST_TF32`，存储及累加保持 fp32。描述符、算法和 scratch 在计划准备阶段固定；库调用捕获为 Graph 子图。TF32 是允许采用的乘法精度，实际核函数由库选择。[NVIDIA 数值策略](https://docs.nvidia.com/cuda/archive/13.0.3/cublas/index.html)、[PyTorch 精度设置](https://docs.pytorch.org/docs/stable/notes/cuda.html)定义了本次对照使用的控制项。

Fuga 的原生图收集直接返回 storage，执行结果直接发布到待计算节点，减少中间 Tensor 包装。身份输入投影在准备时绑定；CUDA 端口描述在原生对象中预先构建，提交边界集中完成 shape/dtype、外部 stream 和 owner 处理。ASK 预先生成独立输出分配表及别名约束，`run` 与 `submit` 共用已绑定计划的 enqueue，执行步骤循环维持原来的调度逻辑。

## 测量方法

硬件为 Xeon E5-2696 v4、RTX 3080 10 GiB，系统为 WSL2。两个框架共用 Python 3.12.15；Torch 为 2.14.0+cu130，CPU 构建使用 MKL。CPU 计算与 CUDA 宿主提交均固定到核心 2，两个框架均设为单线程，Torch 使用 inference mode。

每个配置使用独立进程及临时编译缓存，预热至少 10 次且至少 1 秒，记录 31 次调用，重复三轮并轮换后端顺序。表中数值为各轮调用中位数的中位数，单位为 μs；CUDA 完整调用包含构图、提交和同步。输入创建、上传和首末数值校验位于采样区间之外，执行计数与实际预热次数逐项核对。

常规负载使用原有二进分数输入；尺寸扩展的 GEMM 使用舍入到输入 dtype 的非二进分数秩一矩阵，以解析参考校验结果。更广的形状、布局、抵消、非有限值、空维度和梯度由独立测试矩阵验证。CUDA 新版与 Torch 同时允许 TF32；另以 `NVIDIA_TF32_OVERRIDE=0` 运行 IEEE 控制组。CPU 对照均使用 fp32，新版 Fuga 使用 OpenBLAS，Torch 使用 MKL。

短预热实验中，1024 阶 CUDA GEMM 的 Fuga 三轮中位数约为 597 μs；将预热延长到 1000 次的单轮诊断为 187 μs，Torch 为 161 μs。正式对照因此统一采用持续预热。矩阵描述及对齐候选的临时验证代码已撤回，最终 SDK 的运行库摘要与通过回归的构建一致。


<a id="validation"></a>

## 构建与回归

ASK 的 7 项 CTest 全部通过，包括 TF32 误差界、CUDA Graph、公开端口和重复输出契约。OpenBLAS 的原生链接测试在一个编译模块中生成 432 格数值组合；独立 Compiler SDK 消费测试 3/3 通过。

Fuga 前端 583 项数值与生命周期超集全部通过，用时 975.18 秒；最终 SDK 后端 80 项、pure/all wheel 安装 2 项均通过，全部零跳过。预热与基准工具的 29 项纯测试另行通过。当前默认 CPU 收集 335 项，启用 CUDA/Triton 后收集 595 项；集合关系和原测试契约映射保存在[验证清单](assets/blas-tf32-optimization/validation/pytest-migration.json)。

默认矩阵按因素生成：CPU GEMM 从 1536 行交叉组合收敛为 26 行两两覆盖，加上 27 行定向边界；attention 默认 8 行；完整组合由 `--exhaustive` 选择。端口快照、外部 owner、定义失效、哈希碰撞、并发及混合 dtype 生存期保留定向行为断言。测试使用 pytest fixture、参数化与独立数值参考。

SDK、开发环境与对照环境已重建；安装后的共享库摘要与 SDK 对照记录保存在构建证据中。临时验证脚本、实验包和迁移脚本在归档结果后清理，正式基准保留在 [`tools/benchmark_torch.py`](../tools/benchmark_torch.py)。

## 复现当前对照

```bash
python tools/benchmark_torch.py --backends fuga torch_eager \
  --workloads matmul --matmul-sizes 16 128 512 1024 \
  --matmul-data general --matmul-precision tf32 \
  --threads 1 --cpu-core 2 --rounds 3 --samples 31 \
  --warmup 10 --warmup-seconds 1 \
  --output build/benchmarks/matmul-steady
```

将 `--matmul-precision` 改为 `ieee` 可生成同精度控制组。当前默认测试入口为 `python -m pytest -q`，CUDA/Triton 为 `python -m pytest --triton -q`；后端契约单独执行 `python -m pytest tests/backend --cuda -q`。

构建摘要与库一致性见[最终产物](assets/blas-tf32-optimization/provenance/final-artifacts.json)，完整测量核对见[数据汇总](assets/blas-tf32-optimization/steady/summary.json)。生产改动的主要提交为 ASK `7059129`、`1728bcb`、`ccb653e`，Fuga `cbc3902`、`681d2f9`、`16d2621`、`38af906`。
