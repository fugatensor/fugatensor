# Fuga 热调用性能剖析与优化

后续 LLVM 协作归约与 C++ 图收集的结果见[下一轮优化报告](LLVM归约与原生图收集优化.md)。

2026-11-04，完成 ASK 与 Fuga 的分层剖析、优化、重建和对照。CPU 128 × 128 FP32 矩阵乘法的完整热调用由 **2254.51 μs 降至 187.99 μs，改善 11.99 倍**；同轮 Torch eager 为 71.28 μs，剩余差距为 2.64 倍。CPU 大尺寸逐元素负载为 Torch eager 耗时的 0.84 倍。

本轮修改代码：ASK `c47cde6`，Fuga `94004ff`。逐元素融合、自动微分、公开 API 和 ASK/Fuga 的项目边界保持原有契约。

## 修改方案与落地结果

| 位置 | 瓶颈 | 已落实的修改 |
| --- | --- | --- |
| ASK Host 目标代码生成 | 发出机器码前缺少目标相关的循环与向量优化 | `HostObject` 运行 LLVM O3 pipeline；关闭浮点乘加收缩 |
| ASK CPU matmul | 每个输出独立沿 K 做标量累加，B 读取重复，列方向并行未利用 | 每批次生成 4 行 × 16 列的累加块，四行共享 B 读取；静态生成尾行、尾列 |
| ASK 复合图 | 下游重复消费 matmul 结果会重复计算 | 活跃中间矩阵物化一次，复用现有临时区生存期分配；直接返回的矩阵写入公开输出 |
| Fuga 原语构图 | 每次原语调用走通用签名绑定、默认参数展开和重复元信息检查 | 原语预先保存参数布局、输出类型；匹配后的模板直接绑定待计算结果；编译输入投影固定执行元信息 |

通用用户函数仍保留完整签名语义。Engine 所属关系在调用边界检查，类型与形状规则在首次追踪时验证。矩阵块选择、尾块尺寸和临时区布局在编译期确定，生成的执行循环只承担计算与必要的循环控制。

CPU matmul 每个输出沿原 K 次序累加，乘法和加法分别舍入；FP16 扩为 FP32 累加，结果最后舍入到 FP16。CPU 类型集合仍为 bool、i32、i64、f32、f16。

## 时间花在哪里

分层测量独立于正式速度对照。每项预热 5 次、采集 21 次，先测无插桩的构图与求值，再测诊断包装器，最后测预分配缓冲区的原生调用。

CPU large 负载，单位 μs，表中为优化前 → 优化后：

| 负载 | Python 构图 | 求值到返回 | 预分配原生计算 |
| --- | ---: | ---: | ---: |
| 逐元素 | 116.13 → 61.80 | 251.79 → 140.80 | 142.06 → 46.45 |
| 8 层归约链 | 747.01 → 397.40 | 2644.43 → 540.12 | 2407.10 → 305.57 |
| 4 分支汇合 | 449.19 → 242.26 | 1686.26 → 411.55 | 1484.49 → 215.66 |
| 128 阶 matmul | 53.85 → 21.33 | 2220.86 → 182.74 | 2121.08 → 129.34 |

优化前 matmul 原生调用约占同组完整时间的 93%，首要瓶颈在生成的计算代码。单独加入 O3，原生 matmul 只降至 1975.68 μs；列向量化和行复用才进一步消除标量累加的限制。1 × 16 与 4 × 16 的独立三轮比较中，128 阶连续 FP32 原生调用由 277.41 降至 156.73 μs，连续 FP16 由 1818.02 降至 566.39 μs。

缓存命中时，最终版本 CPU 四类负载的字典查找仅约 2–7 μs。依赖收集、定义依赖处理与结构键生成仍需遍历图；归约链对应三项分别约 80、43、35 μs。继续叠加缓存字典收益有限，下一步应减少生成键之前的重复结构工作。

CPU 输出分配约 11 μs（128 阶 matmul）或 33–37 μs（512 × 256 输出）；原生函数调用包装与 Engine 包装各约 9–16 μs。CPU 经生成函数的 C ABI 调用，不经过 CUDA Session 的提交路径。

CUDA 的主要改善来自构图：归约链由 706.86 降至 368.27 μs，分支汇合由 459.21 降至 239.65 μs。最终版本预分配的 ASK 原生提交在四项负载中约 16–28 μs；本轮没有修改 CUDA 调度器，提交计时未呈现稳定改善。普通公开调用还包含输出分配、端口绑定与完成回收，这部分由独立的诊断记录保留。

各层中位数来自不同测量阶段，诊断包装器自身也有开销；因此这些数字用于定位量级，整体速度以三轮无插桩对照为准。CPU 原生计时含 ctypes 调用桥；CUDA 提交到同步完成的时间含等待与回收，设备计算另由 CUPTI 记录。

## CUDA 提交与设备计算

Nsight Systems 单独采集优化前、最终版本与 Torch eager，交叉四类负载、两档尺寸，共 24 项、504 次调用。通过 CUDA API 的 correlationId 将 kernel 对应到每次调用，得到稳定的 kernel 数量。large 负载如下：

| 负载 | Fuga kernel 数 | Torch eager kernel 数 |
| --- | ---: | ---: |
| 逐元素 | 1 | 4 |
| 归约链 | 9 | 16 |
| 分支汇合 | 5 | 11 |
| matmul | 1 | 1 |

Fuga 优化前后的数量相同，逐元素融合已经生效。单 kernel 的逐元素计算在采集下约 2.11 μs，Torch 四个 kernel 合计约 7.68 μs；两者 matmul kernel 均约 5.31 μs。结合约 138 μs 的 Fuga matmul 完整热调用，进一步优化应优先关注构图、绑定、提交和同步路径。

Graph 节点追踪对归约链的扰动很大：采集得到的最终版本 kernel 时长合计 717.69 μs，但另一次无 CUPTI、预分配缓冲区的直接提交到完成仅 224.96 μs。补充 CUDA event 计时的设备时间线窗口为 186.27 μs，进一步确认采集时长不能代表普通运行。分支汇合的这两个交叉检查值分别为 193.70、160.77 μs。

CUDA event 窗口包括主机入队间隙，空事件对自身约 7 μs；matmul 窗口波动为 11.26–161.79 μs。因此设备诊断用于确认计算结构与量级，框架速度比较统一采用前节的无插桩完整调用。原始 kernel 时长、时间线窗口和调用时间分别保留。

## CPU 矩阵尺寸扩展

补充测试以 FP32 连续方阵生成 64、128、256、512 阶组合，每项三轮、预热 5 次、采样 21 次，共 36 项，仍为单线程 CPU。完整调用时间如下，单位 μs：

| 阶数 | Fuga 优化前 | Fuga 最终 | Torch eager | Fuga 改善 | 最终 Fuga / Torch |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 | 336.30 | 83.34 | 10.76 | 4.04× | 7.75× |
| 128 | 2251.95 | 243.08 | 72.07 | 9.26× | 3.37× |
| 256 | 28597.18 | 2365.43 | 508.20 | 12.09× | 4.65× |
| 512 | 330915.53 | 25091.52 | 3713.88 | 13.19× | 6.76× |

128 阶在这组独立运行中为 243.08 μs，三轮范围 240.40–243.34 μs；主对照为 187.99 μs。两组预热、采样长度与运行时段不同，数据分别保留。改善方向一致，稳定幅度应结合两组判断。

Torch 使用 MKL 与 AVX2。当前 ASK 的 4 × 16 块改善了寄存器复用，大尺寸仍需进一步处理缓存层次和数据访问。ASK 保持顺序累加与独立舍入；实测将 `[-1, 1+2^-23] · [1, 1-2^-23]` 扩展为矩阵计算，ASK 均为 0，当前 Torch 的前 16 列约为 `-1.42e-14`，尾列为 0。引入 CPU BLAS 前需要明确其数值契约，不能直接把差距全部归因于框架包装。

## 首次调用与内存成本

O3 增加冷编译工作。CPU large 的首次完整调用包含编译与首次执行：逐元素 235.6 → 237.9 ms，归约链 255.1 → 321.9 ms，分支汇合 245.5 → 290.3 ms，matmul 231.6 → 247.1 ms。small 分支汇合由 249.5 增至 522.5 ms，是本组最明显的冷启动代价；短生命周期任务应同时评估这一成本。

CPU 直接 matmul 的 ABI 临时区为 0；large 归约链与分支汇合分别为 4096、8192 字节，均与优化前相同。中间 matmul 按活跃消费关系物化一次，其容量和复用位置由静态计划决定。

CUDA ASK 分配池的峰值与优化前相同：large 逐元素 1,048,576 字节，归约链 1,052,672 字节，分支汇合 4,196,352 字节，matmul 196,608 字节。该指标覆盖 ASK 自有池；Torch caching allocator 的统计边界不同，各自原始数值保留在 CSV。

进程峰值 RSS 包含编译器、框架、输入和独立参考。主对照的 CPU large Fuga 为约 60.5–86.5 MiB；独立尺寸扩展测试中最终版本相对基线增加约 16.5–18.7 MiB。该指标用于描述进程整体占用，张量临时区依据 ABI 单独报告。

最终机器码抽查覆盖 128 × 128 与 128 × 17 输出：出现向量乘法与加法，FMA 指令为 0，向量栈读写为 0；三个条件跳转分别承担必要的计算循环。证据：[机器码审计](assets/hotpath-optimization/native-code-audit.json)。

## Python 层是否过厚

对小负载和部分 CUDA 负载，是。原语构图已接近减半，但缓存命中仍需完成节点收集、定义依赖处理、结构键创建、端口包装和结果对象创建。这些是可测量的重复工作；继续增加缓存层数并不会消除它们。

下一轮建议按下表推进；这些是待验证方案：

| 优先级 | 修改位置与做法 | 保留的语义与验证条件 |
| --- | --- | --- |
| 1 | `_lazy` 在已求得输出需求的拓扑排序过程中收集规范输入编号、结构键片段与活跃定义集合，减少后续独立遍历和临时容器 | 多输出需求先求固定点；测试共享节点、部分输出、未使用输入和长链 |
| 2 | 不可变原语模板保存可复用的结构片段与定义依赖集合，热调用绑定当前 Tensor；减少重复元组与元信息对象创建 | 普通 Python 每次执行；输入别名、shape/dtype、定义变更仍参与缓存语义；缓存不延长无关输出存储寿命 |
| 3 | 依据剩余剖析结果，将稳定的绑定和图遍历算法整体移入 Fuga 原生模块，减少 Python/C++ 往返 | 算法留在 Fuga 层，ASK 继续接收数值图和执行计划；仅在端到端收益覆盖维护成本时采用 |

大矩阵另在 ASK Host 降级内评估缓存分块与打包的成本选择，并保持每个输出的累加顺序。CUDA 侧优先检查原生提交外的绑定与资源包装成本。两类工作分别针对框架固定成本和实际计算成本，按尺寸矩阵独立验证。
